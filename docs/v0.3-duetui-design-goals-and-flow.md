# CoDesign Agent v0.3 设计目标与步骤流程

> 版本定位：从「会流式对话的设计思维训练 App」升级为「Duet-style 双向共创式设计澄清工作台」。  
> 核心目标：保留 v0.2.1 已经跑通的大模型流式回复与结构化提取能力，但不再把主体验呈现为通用聊天框，而是将 AI 追问、用户回答、字段确认、阶段推进和设计产物更新整合为一个可操作的任务型界面。

---

## 01｜v0.3 版本定位

v0.2.1 已经完成了真实大模型接入、流式回复、Markdown 渲染、设置页配置、键盘交互优化，以及从对话中提取 DesignBrief、Progress 和 Insights 的基础能力。  
因此 v0.3 不应继续优先做 Keychain、多模型管理、导出、Token 统计等工程增强，而应优先解决一个更关键的产品问题：

> 当前界面仍然容易被理解为「普通 AI 聊天框 + 右侧总结」，而不是一个专门用于设计思维训练和设计类课程开题澄清的智能 Agent。

v0.3 的任务是完成一次主体验重构：

```text
Chat-based Experience
↓
Duet-style Design Clarification Workspace
```

也就是说，AI 仍然通过语言与用户交流，但用户看到和操作的主界面不应是无限消息流，而应是由 AI 和用户共同推进的设计澄清工作台。

---

## 02｜理论依据：从 DuetUI 到 CoDesign Agent

DuetUI 提出的核心思想是：在复杂、多步骤、意图模糊的任务中，用户的真实意图并不是在一开始就完全确定的，而是在与系统持续交互的过程中逐步显现、修正和收敛。

这与 CoDesign Agent 的应用场景高度一致。设计类课程项目的前期任务通常具有以下特点：

- 用户一开始只有模糊想法，而不是完整需求；
- 用户不知道自己缺少哪些信息；
- 用户需要在回答、反思、修改中逐步明确设计方向；
- AI 不能简单代写方案，而应通过追问帮助用户形成设计判断；
- 设计产物不是一次性生成，而是随着澄清过程逐步生长。

因此，CoDesign Agent v0.3 采用「双向共创式界面」作为核心设计方向：

```text
用户输入模糊设计想法
↓
AI 将任务拆解为阶段、问题和可填写字段
↓
用户通过回答、确认、编辑、选择、跳过等方式操作界面
↓
系统把用户操作记录为 Action History / LearningTrace
↓
AI 基于文本回答 + 操作历史继续追问
↓
DesignBrief / Boundary / MVP / Risk / Metrics 实时更新
```

这里的重点不是「AI 输出更多内容」，而是「AI 把模糊任务转译成可操作的设计界面」，并让用户的操作反过来影响 AI 的下一步行为。

## 03｜v0.3 设计目标

### 目标 1：弱化通用聊天框感

v0.3 后，ProjectDetailView 不应再以 ChatPanel 作为视觉中心。  
聊天记录可以保留，但应降级为 Process Log，而不是主界面。

新的主界面中心应是：

- 当前澄清阶段；
- 当前 AI 追问卡片；
- 当前正在补全的设计字段；
- 用户的回答与选择入口；
- 实时更新的设计产物卡片。

### 目标 2：让 AI 的追问变成可解释的设计动作

AI 的问题不应只是「一句聊天回复」，而应被包装为 Current Clarification Card。每张追问卡片需要说明：

- 当前属于哪一个设计阶段；
- AI 正在帮助用户澄清什么；
- 为什么这个问题重要；
- 用户回答后会更新哪些字段；
- 用户可以回答、跳过、要求示例或修改方向。

### 目标 3：让用户不仅能输入文字，也能直接操作设计产物

v0.3 中，用户的交互不应只发生在输入框里。  
用户还应能对结构化卡片进行操作，例如：

- 确认目标用户；
- 编辑核心痛点；
- 将某功能标记为 MVP 内 / MVP 外；
- 调整风险等级；
- 标记某个验收标准是否可量化；
- 对 AI 提取结果点击「不准确，重新提取」。

这些操作应被记录下来，并参与后续 AI 追问。

### 目标 4：让 9 阶段流程从展示组件升级为导航系统

当前 9 阶段进度如果只是一个可视化条，会比较像装饰。  
v0.3 中，9 阶段应成为工作台的骨架：

- 当前阶段高亮；
- 已完成阶段显示完成状态；
- 缺信息阶段显示空缺提示；
- 用户可以点击阶段查看该阶段的已有信息；
- AI 的下一步追问与当前阶段关联；
- InsightsPanel 按阶段组织产物。

### 目标 5：形成可用于课程展示的视觉证据

v0.3 应直接服务最终展示。老师和同学应能从界面一眼看出：

- 这不是套壳 ChatGPT；
- 它有明确的设计流程；
- 它能帮助用户从模糊想法走向结构化方案；
- 它把 AI 的推理和用户的设计行为可视化；
- 它满足课程对统一设计语言、自定义组件、动画、手势和视觉反馈的要求。

## 04｜v0.3 核心用户流程

### 流程 A：新建项目

```text
进入 ProjectListView
↓
点击 New Project
↓
进入 Design Seed 创建页
↓
用户输入一个模糊设计想法
↓
可选填写：课程类型 / 项目期限 / 技术限制 / 目标用户初猜
↓
点击 Start Clarification
↓
系统创建项目并进入 Clarification Workspace
```

NewProjectView 不应只是普通标题输入页，而应像一个 Design Seed Card。它收集的是「模糊起点」，不是完整需求。

---

### 流程 B：进入设计澄清工作台

```text
进入 ProjectDetailView
↓
顶部显示项目标题、成熟度、当前阶段
↓
左侧或顶部显示 9-stage StageRail
↓
中央显示 Current Clarification Card
↓
下方显示 Answer Composer
↓
右侧或下方显示 Insight Cards
↓
历史聊天折叠到 Process Log
```

主视觉中心是 Current Clarification Card，而不是消息气泡列表。

---

### 流程 C：AI 提问与用户回答

```text
AI 根据当前 DesignBrief 和缺失字段生成追问
↓
追问被渲染为 Current Clarification Card
↓
用户可以：
1. 输入自然语言回答
2. 选择 AI 给出的建议选项
3. 点击「我还不确定」
4. 点击「给我一个例子」
5. 点击「换个角度问」
↓
系统提交用户输入
↓
LLM 流式生成反馈
↓
StructuredExtractor 更新结构化字段
↓
StageProgress 更新阶段状态
↓
InsightCardsPanel 更新设计产物
↓
LearningTrace 记录本轮认知动作
```

---

### 流程 D：用户直接操作设计产物

```text
用户看到 AI 提取出的字段卡片
↓
点击字段卡片
↓
执行编辑 / 确认 / 标记错误 / 移入 MVP 外
↓
系统记录用户操作
↓
Action History 更新
↓
下一轮 AI 追问读取这些操作
↓
AI 避免重复追问，转向更缺失或更高价值的问题
```

这一步是 v0.3 区别于普通聊天框的关键。

---

### 流程 E：查看过程记录

```text
用户点击 Process Log
↓
展开历史对话与行为轨迹
↓
看到：
- 用户原始回答
- AI 追问
- 字段更新
- 阶段推进
- 用户确认 / 修改记录
↓
用户可折叠返回工作台
```

Process Log 的意义不是替代聊天，而是把聊天降级为「可追溯的过程记录」。

---

## 05｜建议的信息架构

### ProjectListView

职责：项目入口与总览。

建议改动：

- 项目卡片显示当前成熟度、当前阶段、最近更新时间；
- 空状态改为引导式文案，例如「从一个模糊想法开始」；
- 增加轻量动画：新增项目卡片从底部浮入；
- 项目卡片支持长按预览或长按编辑；
- 保留设置入口。

### NewProjectView / DesignSeedView

职责：收集模糊设计起点。

建议字段：

- 项目一句话想法；
- 课程 / 作业类型；
- 初始目标用户；
- 已知限制；
- 希望 AI 帮助的方向。

不要求用户一次填全。页面应明确告诉用户：

> 不用想清楚，先写下你现在的模糊想法，AI 会一步步帮你澄清。

### ProjectDetailView

职责：承载完整澄清过程。

建议布局：

```text
WorkspaceHeader
StageRail
CurrentClarificationCard
AnswerComposer
InsightCardsPanel
ProcessLogDisclosure
```

### InsightsPanel

职责：展示设计产物，而不是普通总结。

建议分为：

- DesignBrief Summary；
- MVP Boundary；
- Feature Map；
- Risk Matrix；
- Success Metrics；
- LearningTrace Timeline。

## 06｜建议新增 / 调整的核心组件

### 1. `ClarificationWorkspaceView`

替代原来以 ChatPanel 为中心的布局。  
它负责组织工作台整体结构。

子组件：

- `WorkspaceHeader`
- `StageRail`
- `CurrentClarificationCard`
- `AnswerComposer`
- `InsightCardsPanel`
- `ProcessLogDisclosure`

---

### 2. `CurrentClarificationCard`

v0.3 最核心组件。

显示内容：

- 当前阶段名称；
- AI 当前追问；
- 问题解释；
- 关联字段；
- 推荐回答方式；
- 操作按钮。

示例结构：

```text
阶段 1｜痛点与场景锚定

AI 想确认：
你的设计对象到底是谁？他们在什么具体场景下遇到这个问题？

为什么要问：
如果目标用户和使用场景不清楚，后续功能边界会变得非常泛。

本轮可能更新：
targetUser / painPoint / useScenario

操作：
[回答] [给我例子] [我还不确定] [换个角度问]
```

---

### 3. `AnswerComposer`

不只是普通输入框，而是回答工作区。

包含：

- 多行输入；
- 发送按钮；
- 快捷 chip；
- 「补充一点」；
- 「跳过」；
- 「我不确定」；
- Loading 状态；
- 禁用状态视觉反馈。

---

### 4. `StageRail`

把 9 阶段做成导航与状态系统。

状态：

- locked：未到达；
- active：当前阶段；
- partial：已有信息但不完整；
- complete：已完成；
- warning：存在风险或缺失。

交互：

- 点击阶段查看该阶段信息；
- 长按阶段显示解释；
- 当前阶段变化时有轻量动画。

---

### 5. `InsightCardsPanel`

把结构化提取结果卡片化。

卡片类型：

- 用户与痛点卡；
- 场景卡；
- 核心价值卡；
- MVP 边界卡；
- 功能模块卡；
- 技术方案卡；
- 验收标准卡；
- 风险卡；
- 里程碑卡。

每张卡片都至少支持：

- 查看；
- 编辑；
- 确认；
- 标记不准确。

---

### 6. `ProcessLogDisclosure`

折叠历史消息与操作轨迹。

默认折叠，避免页面看起来像聊天软件。  
展开后显示：

- AI 追问；
- 用户回答；
- 字段更新；
- 用户操作；
- 阶段变化。

---

## 07｜数据与状态设计建议

v0.3 应尽量避免大规模重构 SwiftData 模型。  
优先用现有 `LearningTrace` 或新增轻量结构记录用户操作。

建议新增概念：

```swift
enum UserWorkspaceActionType {
    case answerSubmitted
    case fieldConfirmed
    case fieldEdited
    case fieldRejected
    case stageSelected
    case questionSkipped
    case exampleRequested
    case boundaryChanged
}
```

每次用户操作可记录：

```text
actionType
timestamp
stageOrder
targetField
oldValue
newValue
source
```

这些记录后续可以作为 prompt context：

```text
Recent user actions:
- Confirmed targetUser as "design students"
- Moved "PDF export" outside MVP
- Marked successMetrics as unclear
```

## 08｜v0.3 开发步骤

### Step 1：建立 Design System

目标：先统一视觉语言，避免后面每个页面各写各的。

建议新增：

```text
Views/DesignSystem/AppTheme.swift
Views/DesignSystem/AppCard.swift
Views/DesignSystem/AppButton.swift
Views/DesignSystem/StatusBadge.swift
Views/DesignSystem/StagePill.swift
Views/DesignSystem/SectionHeader.swift
```

验收标准：

- 所有新卡片使用统一圆角、阴影、间距；
- 主色、辅助色、背景色集中定义；
- 至少有 Primary / Secondary / Ghost 三类按钮；
- 不再大量依赖系统默认样式。

---

### Step 2：改造 ProjectListView

目标：让首页更像一个设计项目工作台，而不是普通列表。

改动：

- 项目卡片显示当前阶段与成熟度；
- 空状态卡片美化；
- 新增项目动画；
- 长按项目卡片进入编辑或预览；
- 滑动删除保留。

验收标准：

- 满足至少一种手势；
- 有新增 / 删除动画；
- 项目状态一眼可读。

---

### Step 3：改造 NewProjectView 为 DesignSeedView

目标：让新建页从「创建标题」变成「输入模糊设计起点」。

改动：

- 增加 Design Seed Card；
- 文案强调“不需要一次想清楚”；
- 提供若干提示 chip；
- 支持已知限制输入；
- 创建后直接进入工作台。

验收标准：

- 用户不用理解复杂表单；
- 页面能体现“从模糊想法开始”；
- 创建项目后能触发第一轮 AI 澄清。

---

### Step 4：创建 ClarificationWorkspaceView

目标：搭建 v0.3 主界面骨架。

改动：

- ProjectDetailView 中新增 workspace tab 或直接替换 chat tab；
- 将 ChatPanel 降级为 ProcessLog；
- 中央显示 CurrentClarificationCard；
- 下方显示 AnswerComposer；
- 保留原有 ViewModel 逻辑，减少破坏。

验收标准：

- 主视觉不再像普通聊天框；
- AI 回复仍可流式显示；
- 用户回答仍能触发现有 sendMessage 流程。

---

### Step 5：实现 CurrentClarificationCard

目标：将 AI 当前追问卡片化。

改动：

- 从最近一条 assistant message 中读取当前追问；
- 显示当前 stage；
- 显示关联字段；
- 显示「为什么问」说明；
- 提供操作按钮。

短期可以先做静态映射：

```text
stageOrder 1 → targetUser / painPoint / useScenario
stageOrder 2 → coreValue / differentiation
stageOrder 3 → boundaryItems / mvpFeatures
...
```

验收标准：

- 用户能知道 AI 为什么问；
- 用户能知道回答会影响什么；
- 卡片有加载状态和完成状态。

---

### Step 6：实现 InsightCardsPanel 可操作化

目标：让结构化字段从“只读总结”变成“可操作设计产物”。

改动：

- 每个字段显示为独立卡片；
- 支持点击编辑；
- 支持确认字段；
- 支持标记不准确；
- 修改后更新 SwiftData。

验收标准：

- 用户可以不通过聊天直接修正 AI 提取结果；
- 修改后界面立即反馈；
- 操作被记录到 LearningTrace 或 ActionHistory。

---

### Step 7：实现 ProcessLogDisclosure

目标：保留对话可追溯性，但不让聊天成为主体验。

改动：

- 默认折叠；
- 展开后显示历史消息；
- 用户行为轨迹与消息穿插显示；
- 支持滚动查看。

验收标准：

- 默认界面不再像聊天 App；
- 用户仍能查看完整过程；
- 历史记录不影响主任务界面清爽度。

---

### Step 8：补充状态反馈、动画与手势

目标：满足课程交互要求，也增强产品完成度。

建议实现：

- Stage 切换动画；
- InsightCard 更新时轻微高亮；
- 发送按钮 loading 状态；
- 字段确认后的 checkmark 动画；
- 长按 Stage 查看解释；
- 滑动卡片标记 MVP 内 / 外；
- 错误状态 Toast 或 Inline Warning。

验收标准：

- 至少 2 种手势；
- 至少 2 种动画；
- 至少 3 类明确状态反馈：loading / success / warning。

---

## 09｜v0.3 暂不做事项

为了控制开发风险，v0.3 暂不优先做：

- Keychain 安全存储；
- 多模型配置管理；
- PDF / Markdown 导出；
- Token 使用统计；
- 多 Agent 架构；
- 大规模重写 PromptTemplates；
- 大规模 SwiftData 迁移；
- 完整拖拽式白板。

这些都可以进入 v0.4 或最终增强版。  
v0.3 的核心任务只有一个：

> 把主界面从聊天框改造成双向共创式设计澄清工作台。

## 10｜v0.3 验收清单

### 产品体验验收

- [ ] 用户进入详情页后，第一眼看到的是工作台，而不是聊天记录；
- [ ] AI 当前追问以卡片形式呈现；
- [ ] 每个追问能说明关联阶段和关联字段；
- [ ] 用户能通过文字回答，也能通过按钮 / chip / 字段编辑操作界面；
- [ ] 结构化设计产物能实时更新；
- [ ] 历史对话默认折叠为 Process Log；
- [ ] 9 阶段流程能作为导航与状态系统使用。

### 技术验收

- [ ] 不破坏现有 Live API 流式回复；
- [ ] 不破坏 Mock 模式；
- [ ] 不破坏 SwiftData 持久化；
- [ ] iOS Simulator 编译通过；
- [ ] macOS Designed for iPad 编译通过；
- [ ] 不硬编码 API Key；
- [ ] 不进行不必要的大规模数据模型迁移。

### 课程要求验收

- [ ] 至少 3 个页面：列表页、新增页、详情页；
- [ ] 本地数据持久化；
- [ ] 统一配色、字体层级、圆角、阴影；
- [ ] 使用自定义按钮、卡片、输入框；
- [ ] 至少 2 种手势；
- [ ] 至少 2 种动画；
- [ ] 有清晰 loading / success / warning 视觉反馈；
- [ ] 设计文档能解释理论依据与设计合理性。

## 11｜给 Claude Code / CodeX 的总提示词

## 12｜最终展示叙事

v0.3 完成后，展示时可以这样讲：

> 我们最初做出了一个能够真实调用大模型、进行苏格拉底式追问并提取 DesignBrief 的 App。但经过老师反馈与文献启发，我们意识到，如果界面仍然是普通聊天框，它就很难体现设计类课程开题澄清的独特性。因此 v0.3 将主体验从聊天界面改造为双向共创式设计澄清工作台。AI 不只是输出文本，而是把用户的模糊想法拆解为设计阶段、追问卡片和可操作字段；用户也不只是输入 prompt，而是通过回答、确认、编辑、标记边界等方式逐步塑造自己的设计方案。这个过程既保留了大语言模型的灵活性，也避免了纯表单流程的僵硬，体现了“框而不死，活而不乱”的产品理念。
